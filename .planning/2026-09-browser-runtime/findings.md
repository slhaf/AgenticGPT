# Browser Runtime V1 — Findings

## 1. AppState and long-lived ownership

- `crates/agentic-gpt/src/state.rs:147` defines `pub(crate) struct AppState`. Shared mutable/lifecycle state is represented by `Arc<...>` fields (for example `jobs`, `mcp_concurrency`, `skill_leases`, and `skill_installs`); `AppState` itself is `Clone`.
- The production constructor is `crates/agentic-gpt/src/main.rs:build_app_state` (around line 270). It prepares persistent paths, opens `JobHistoryStore`, then constructs each manager once inside the `AppState` literal. `run_hub`, `run_stdio_worker`, and `run_local` call it (`main.rs:154`, `main.rs:241`, `main.rs:340`).
- The repository-conventional addition is therefore: add an `Arc`-backed manager field to `AppState`, initialize it in `build_app_state`, and add matching test-state initialization to the `AppState` literals in `agent_info.rs:tests::state`, `stdio_server.rs:tests::test_state`, `main.rs:tests::command_test_state`, `jobs.rs:tests::{test_state,test_state_with_history}`, `room_reads.rs:tests::test_state`, `room_maintenance.rs:tests::test_state`, `skills.rs:tests::test_state`, `skill_installs.rs:tests::test_state`, and `mcp.rs:tests::managed_test_state`. Existing analogous long-lived managers are `jobs.rs:SkillLeaseManager` and `skill_installs.rs:InstallManager`.

## 4. Policy, confirmation, audit, source, results, and cancellation

- Command policy enters through `crates/agentic-gpt/src/policy.rs:policy_decision_for_profile`; it combines `need_confirm`, profile built-ins (`builtin_rules`), and configured `PolicyConfig` rules, returning `PolicyDecision::{Allow,Confirm,Deny}`. Process jobs call it in `jobs.rs:run_async_job` and `start_process_batch`; `tmux.rs:exec` calls it directly.
- Path policy enters through `file_ops.rs:resolve_path` -> `check_policy` (deny/read-only/write-root checks), and `file_ops.rs:apply_patch_inner` revalidates targets before commit. A direct handler should clone `Config` from `state.config` before operation, as `file_ops::edit` and `tmux::exec` do.
- Confirmation anchors are `confirmation.rs:request_confirmation` for direct tools and `request_confirmation_cancellable` for cancellable Jobs. `file_ops.rs:apply_patch_inner` requests confirmation for effective edits; `tmux.rs:{confirmed,exec}` does the same for tmux mutations.
- Audit anchors are `audit.rs:{AuditRecord,write_audit}`, `tmux.rs:audit_tmux`, and `file_ops.rs:{write_patch_audits,write_patch_failure_audit}`. Managed process/MCP lifecycle audit is assembled by `jobs.rs:ManagedAuditContext` and emitted by `jobs.rs:finalize_job`; it records `policy_decision`, confirmation, `request_source`, terminal state/evidence, and bounded result metadata.
- Source attribution is `stdio_server.rs:RequestIngress::source`, producing `local:<tool>` or `tunnel:<tool>`; `dispatch_process_exec`, `dispatch_process_batch`, `dispatch_skill_run`, and MCP dispatch use it. Tests `stdio_server.rs:{local_skill_audit_uses_local_request_source,local_mcp_call_audit_uses_local_request_source,tunnel_skill_audit_uses_tunnel_request_source}` verify this convention.
- Structured direct values use `{"error":{"code","message"}}`: `file_ops.rs:FileError::value` plus free function `file_ops.rs:to_result`, `stdio_server.rs:{structured_error_value,structured_error_from_reason,job_error}`, and `local_service.rs:{dispatch,room_toolset_required_error,profile_capability_required_error}`. rmcp wrapping is `ServerHandler::call_tool`, which selects `CallToolResult::{structured,structured_error}`.
- Bounded waits/cancellation are explicit: process Jobs use `jobs.rs:{cancel_job,cancel_mcp_job,wait_for_job}` and `AtomicBool` cancellation; MCP uses `mcp.rs:run_managed_call` with `tokio::time::sleep_until`, `Peer::notify_cancelled`, two-second notification/close bounds, and `close_client`. Direct bounded waits include `stdio_server.rs` wait caps and `confirmation.rs:CONFIRM_TIMEOUT_SECS` paths.

## 5. Persistent-resource/process and rmcp evidence

- Closest repository-owned long-lived manager pattern is `crates/agentic-gpt/src/skill_installs.rs:InstallManager`: `Arc`-shared maps/semaphore/locks/Notify, `start`, `recover`, cancellation, durable records, and `AppState::skill_installs` ownership. `jobs.rs:SkillLeaseManager` is the smaller per-resource keyed-lock pattern; test `jobs.rs:skill_leases_still_block_updates` proves shared/exclusive serialization. `tmux.rs:{create_session,close_session,list_sessions,list_panes}` demonstrates an existing named external persistent resource, but it is discovered/controlled through CLI calls rather than an AppState-owned manager.

The stdio client branch uses `TokioChildProcess` (`mcp.rs:1539-1548`), and tests inject a factory via `fake_factory`/`routing_factory`; this is reusable transport/test evidence, not a persistent lifecycle.

No current MCP client is an AppState-owned persistent client.

### 3. MCP session contract

- Initialize is JSON-RPC 2.0 request `{jsonrpc:"2.0", id, method:"initialize", params:{protocolVersion:"2025-06-18", capabilities:{}, clientInfo:{name:"agentic-chrome-control-poc", version:"0.1"}}}`. The PoC rejects a response containing top-level `error`, then sends the notification `{jsonrpc:"2.0", method:"notifications/initialized", params:{}}`.
- A JavaScript call is `{jsonrpc:"2.0", id, method:"tools/call", params:{name:"js", arguments:{code, timeout_ms}, _meta:{"x-codex-turn-metadata":{session_id, turn_id}}}}`. The `_meta` is on `tools/call.params`, alongside `name` and `arguments`, not inside the JS arguments.
- The PoC creates one `session_id` and one `turn_id` when the bridge/kernel object is constructed and reuses them for every call in that process. The lease-stable evidence is therefore the initialized MCP process/kernel and these metadata values across calls. The four-tool evidence and reset docs do not establish whether either ID changes after `turn_ended`/`js_reset`; that reset-ID policy is unresolved.
- The only verified `turn_ended` call shape outside the PoC is the official Stop hook input `{hook_event_name, session_id, turn_id}`.

### 4. Browser bootstrap contract

- The PoC's exact bootstrap is: if `globalThis.agent == null`, `const { setupBrowserRuntime } = await import(JSON.stringify(browserClientPath)); globalThis.agent = await setupBrowserRuntime();`; if `globalThis.chrome == null`, `globalThis.chrome = await agent.browsers.get("chrome");`; then `const __browsers = await agent.browsers.list();` and `nodeRepl.write(JSON.stringify({browserId: chrome.browserId, browsers: __browsers}))`.
- The persistent bindings explicitly created by this sequence are `globalThis.agent` and `globalThis.chrome`; `__browsers` is also declared by the bootstrap invocation. No `globalThis.browser` binding is created by the PoC. The intended later Browser SDK object is the `chrome` Browser returned by `agent.browsers.get("chrome")`; `agent` is the root object for browser discovery/documentation.
- The selected `docs/api.json` confirms `Agent.browsers`, `Agent.documentation`, `Browsers.get/list`, and the `Browser` API. The client/service source also confirms that Browser operations use the trusted `nodeRepl` service boundary; the wrapper must not reproduce that private RPC.

### 5. Reset/release contract

- `js_reset` is documented by the current official resources as: reset the persistent CUA JavaScript session, discard all JavaScript bindings, and make the next JS call initialize a fresh runtime. It explicitly does not close browser tabs/native apps or erase their state.
- `turn_ended` is verified as a node-repl MCP tool invoked by the Browser/Chrome Stop hook with `hook_event_name`, `session_id`, and `turn_id`. Local source/docs establish the signaling shape, but not a stronger cleanup guarantee (tab cleanup, service shutdown, idempotence, or wait behavior).
- Current installed node-repl `tools/list` further states that repeated `turn_ended` notifications for the same session/turn pair are ignored. This establishes pair-level deduplication, but still does not establish whether Browser calls after `js_reset` are expected to continue under that same pair or whether a fresh logical turn should rotate `turn_id`. Slice 07 therefore does not invent ID rotation; repeated in-place reset under one persistent kernel remains an explicit installed-runtime smoke item before the model-facing reset surface is considered fully proven.
- The evidence therefore supports using `js_reset` for JS/kernel bindings and `turn_ended` as an official end-of-turn signal. It does not establish that either closes the MCP process, destroys Browser service state, closes tabs, or rotates IDs. Graceful release/reset ordering and failure semantics remain unresolved; process termination is only directly shown by the PoC's separate bounded `terminate`/`kill` close path.

### 6. Result contract

- The PoC returns `response.get("result", {})` from `tools/call` without reshaping it. A top-level JSON-RPC `error` is treated as a bridge error; a tool result's `isError` is preserved and is checked by the bootstrap path.
- Current official docs establish the output channels: `nodeRepl.write(value)` contributes text/serialized values, and `nodeRepl.emitImage(image)` contributes an image; image input may be bytes/file URL or `{bytes, mimeType}`. Browser observations may emit output internally, so callers should not duplicate them.
- A wrapper should preserve the opaque MCP result, including its `content` items and `isError`, rather than reducing it to text. The exact node-repl wire encoding for text chunks, image data/base64 and MIME field names, optional structured fields, and thrown-JavaScript error content is not established by the inspected local docs/source; these are unknowns.

Evidence: `Cargo.lock:2499` names the exact `rmcp` package as `1.7.0` from the crates.io registry; source root is `/home/slhaf/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/rmcp-1.7.0/`.

### 2. `CallToolRequestParams` and `_meta`

- The exact rmcp 1.7.0 shape is `src/model.rs:2956-3009`: `meta: Option<Meta>` (serde name `_meta`), `name: Cow<'static, str>`, `arguments: Option<JsonObject>`, and `task: Option<JsonObject>`. `new`, `with_arguments`, and `with_task` are in the same impl.

### 3. Client operations and cancellation

- `Peer<RoleClient>::notify_cancelled(CancelledNotificationParam) -> Result<(), ServiceError>` is generated at `src/service/client.rs:341-355`; Agentic calls it under two-second timeouts at `crates/agentic-gpt/src/mcp.rs:1283-1290,1304-1310`.

### 4. `TokioChildProcess` command supply/configuration

- `TokioChildProcess::new(command: impl Into<process_wrap::tokio::CommandWrap>)` and `.builder(...)` are `src/transport/child_process.rs:64-78`. `tokio::process::Command` converts to `CommandWrap` via `process-wrap-9.1.0/src/generic_wrap.rs:169-176`.

- `TokioChildProcess` stores private `ChildWithCleanup` and `AsyncRwTransport` fields (`child_process.rs:37-42`). Once converted by `serve`, the service task owns the transport (`src/service.rs:742-750` onward); the running client owns that task.

### 5. Close, drop, and transport shutdown

- `TokioChildProcess`'s `Transport<RoleClient>::close` calls `graceful_shutdown` (`child_process.rs:205-223`). That method takes the child, closes the async transport writer, waits for normal exit for `MAX_WAIT_ON_DROP_SECS = 3`, then calls `ChildWrapper::kill()` if the wait times out (`child_process.rs:44-47,105-135`).
- The rmcp service loop exits on input EOF or service cancellation, drains in-flight handler responses for up to five seconds on `QuitReason::Closed` or two seconds on `QuitReason::Cancelled`, then calls `transport.close().await` (`src/service.rs:786-820,1039-1084`). Explicit `RunningService::close`/`cancel` therefore reaches the child transport close path and waits for service cleanup, subject to errors and that drain path.
- `RunningService::close_with_timeout` returns `Ok(None)` when its supplied wait expires; source does not establish that the child has exited when it returns (`src/service.rs:579-607`).
- Dropping `TokioChildProcess` while its child is present invokes `ChildWithCleanup::drop`, which spawns an asynchronous task calling `ChildWrapper::kill()` (`child_process.rs:44-60`). Dropping `RunningService` relies on `DropGuard` to cancel asynchronously and explicitly says guaranteed cleanup requires `close()` or `cancel()` (`src/service.rs:621-631`). The caller does not await these drop paths.
- Proven: graceful shutdown attempts close, wait up to three seconds, then kill; drop attempts an asynchronous kill. Not proven: that a dropped service has completed child cleanup before return, or that cleanup is bounded from the caller's perspective. Also, if `graceful_shutdown` returns early from `transport.close().await?`, this source does not establish a subsequent wait/kill guarantee.

### 6. Child handle/PID/kill API

- `TokioChildProcess::id() -> Option<u32>` is public (`child_process.rs:99-103`). `TokioChildProcess::into_inner(self) -> Option<Box<dyn process_wrap::tokio::ChildWrapper>>` is also public (`child_process.rs:138-141`).
- The extracted `ChildWrapper` trait exposes `id`, `kill`, `start_kill`, `try_wait`, and `wait` (`process-wrap-9.1.0/src/tokio/core.rs:38-168`). rmcp has no non-consuming `TokioChildProcess::kill` or public `child()` accessor. ### 9. Default client-side handlers

- `ClientInfo` implements `rmcp::ClientHandler` at `src/handler/client.rs:262-270`, overriding only `get_info` to clone itself. Other behavior is trait default behavior.

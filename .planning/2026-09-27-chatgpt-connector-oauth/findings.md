# Evidence

Official OpenAI auth guide https://developers.openai.com/plugins/build/auth : HTTPS protected-resource metadata (canonical resource and AS issuer), 401 Bearer resource_metadata challenge, authorization-server metadata with S256, auth code + PKCE, resource on authorize/token, token audience/scope checks, CIMD or DCR or predefined client, published supported token authentication methods. ChatGPT chooses callback-ID-specific redirect unless issuer response identification is fully implemented; exact callback shown in connector management. Advertise authorization_response_iss_parameter_supported=true only when `iss` included in every success/error authorization response. CIMD prioritized when advertised; DCR still supported. ChatGPT does not support client_credentials/service accounts.

Official setup https://developers.openai.com/plugins/deploy/connect-chatgpt : externally reachable HTTPS streamable MCP URL including /mcp, auth discovery, refresh connector metadata after deployment. General MCP guide https://developers.openai.com/api/docs/mcp also confirms CIMD public-client (`none`) or signed assertion, DCR when configured.

Code findings: `crates/agentic-gpt/src/ingress/http_oauth.rs:289-303` advertises CIMD support; `:491-549` accepts any nonempty client_id while `:560-590` admits any ChatGPT callback-ID path, without verifying the client's metadata document or that redirect appears in `redirect_uris`. Existing e2e test `crates/agentic-gpt/tests/standalone_http_mcp.rs:601-616` uses an arbitrary non-URL client ID. Actual ChatGPT stable metadata https://chatgpt.com/oauth/client.json publishes only the stable `https://chatgpt.com/connector_platform_oauth_redirect` callback and lists both `none` and `private_key_jwt` as supported methods; its singular legacy preference is `private_key_jwt`. Thus an id/redirect combination inconsistent with metadata currently passes. This is a concrete protocol/security deviation; it does NOT establish the reported connection failure.

Potential deployment blocker: default `allowHosts` is loopback-only and `publicUrl` does not add its public authority; `crates/agentic-gpt/src/ingress/http_oauth.rs:692-718` rejects external Host as 403 before OAuth metadata or `/mcp` challenge. Depending on proxy Host forwarding, this may prevent discovery. Preserve DNS rebinding defense and document explicit allowlist; actual runtime/proxy and failing ChatGPT request are unavailable.

Do not assert issuer flag omission is a blocker: official docs specify callback-ID redirect when RFC9207 identification is not advertised, and implementation accepts it; claiming issuer support without `iss` on every response would introduce an actual failure. DCR and refresh grants are optional. Standalone is primary scoped surface; Hub's OAuth is independent and not known to be deployed here.

Worker smoke: `cargo test -p agentic-gpt --test standalone_http_mcp standalone_http_mcp_chatgpt_oauth_discovery_authorize_token_and_mcp_use -- --nocapture` passed (1 passed, 11.43s). The test starts a real standalone worker, fetches both metadata variants, performs PKCE authorization and token exchange, and initializes the authenticated MCP transport. It also proves arbitrary non-URL `client_id` is accepted and OAuth metadata requests with an external unallowlisted Host return 403. It uses a local HTTP listener with an advertised HTTPS URL; it does not prove production TLS/proxy or ChatGPT's live callback.

# 文档标准

## 目的、适用范围与优先级

本文面向维护者和 coding agent，规定项目文档的写作、维护和审查方式。它适用于仓库内现有及新增的 Markdown 页面，以及适用时的 OpenAPI 描述和面向模型的工具定义。历史文档无需因此批量重写；修改某页时，按改动范围使其符合本标准。

文档解释产品行为，但不能改变产品行为。发生矛盾时按以下顺序判断：

1. 当前运行时代码及其实际执行的配置、schema 和协议约束，是已实现行为的首要依据。HTTP/OpenAPI 表面的契约以 `openapi/hub.yaml` 为准；实时 MCP 工具表面以实际暴露的工具及其 schema 为准。
2. 与当前实现相符的用户文档，用于说明受支持的用法、边界和操作步骤。发现不一致时，应核验并修正文档或契约，不能用旧文档覆盖当前事实。
3. 本标准及外部编辑指南只提供写作指导，不定义产品行为或协议要求。

OpenAPI 和实时 MCP 契约分别是其自身表面的权威来源；任何文档都不得把尚未实现的设计或未验证的外部行为写成当前承诺。用 RFC 2119 大写词（`MUST`、`SHOULD`、`MAY` 等）时，仅在明确的规范性要求中使用，并说明要求来源；不要把厂商建议改写成项目或协议的强制要求。

## 文档角色

按读者任务选择已有合适页面，不为同一事实另建重复入口：

- `README.md` 是项目入口，介绍定位、主要使用路径并指向深入文档。若保留 `README.zh-CN.md` 等双语对应页，两页的当前事实、边界和关键链接必须一致；语言不同不得造成行为承诺差异。
- 指南说明读者如何完成一项任务，包含前置条件、按顺序可执行的步骤、预期结果及相关限制。
- 参考文档准确列出接口、配置、命令、schema 或行为细节；以实现或契约为准，避免把参考内容写成教程。
- 版本化迁移和发布说明记录对应版本的变更、影响、迁移步骤及已知限制。标明适用版本，不把历史记录当作当前使用指南。
- 架构设计、决策和计划说明各自的状态。区分已实现事实、已确认决策、推断与建议；计划文档不能暗示规划内容已交付。
- 存档内容保留其历史上下文和状态；若仍可被读者找到，应明确指出它不是当前行为依据，并链接当前入口（如存在）。

## 语言与写法

项目文档使用简体中文：新建页面、以及现有页面新增或改写的正文均以中文撰写。未触及的英文历史页面不要求在本次一次性翻译；修改英文页面时，若局部中英混排影响阅读，应将该页迁移为中文，而不是留下难以维护的混合正文。保留英语的公共 API 名称、代码标识符、命令、协议术语和原始错误文本；首次出现可能有歧义的术语时用中文解释。若现有页面仍有中英文对应版本，应链接两者并保持事实一致。

使用简洁、直接的主动表达。标题描述读者可找到的主题；按任务拆分章节，使用逐级递进的标题，不跳级。步骤使用有序列表，彼此并列的选择或条件使用项目符号。用表格呈现需要横向比较的字段，不将长篇说明塞入表格。说明前置条件、默认值、单位、失败方式和副作用，而非仅列功能名称。

示例必须能安全复制或清楚标记为示意。命令、配置和请求示例应与当前接口相符，不包含真实凭据、可用密钥或误导性的省略；需要占位符时，用明显不可用的值并说明替换方式。不得用虚构输出、未验证的截图或“应当成功”替代验证证据。链接使用有意义的中文描述，优先链接仓库内相关权威页面及官方来源。

## 准确性、安全与版本

文档陈述当前事实时，应能追溯到实现、schema、协议或可复现的操作。必要时链接到具体仓库路径、接口或版本。明确标注尚未验证的内容、适用条件与限制；将事实、推断、决策、建议和计划区分开。避免没有证据支撑的保证、绝对化安全措辞和过期的“当前”日期。

涉及安全时，具体说明信任边界、权限、确认要求、凭据处理及可能的副作用。描述防护机制时写清其适用范围；不要将模型提示、工具注解或用户文档本身描述为运行时强制控制。示例中不得暴露密钥、个人信息或可直接滥用的生产数据。

版本化说明必须清楚标识版本或适用范围。配置项、命令选项、API 字段、工具名称或行为变更时，应说明兼容性和迁移影响；没有迁移影响时无需臆造迁移步骤。历史发布记录不得在无版本语境下陈述为当前状态。

## 面向模型的工具定义

此节适用于模型可调用的工具及其公开描述，不替代协议或 API schema。目标是让模型能够依据用户目标正确选择工具、构造符合契约的输入，并准确预期结果和风险；不是把描述写成营销文案，也不是借自然语言提示代替权限控制。

每个工具应有清楚且彼此可区分的名称和描述。描述须说明工具完成什么，以及适合何种用户目标、何时调用；必要时也说明不适用的目标、不可完成的事或更合适的替代路径。名称应稳定、可识别，避免含糊的泛化名称或只区分编号的近似名称。

输入 schema 和说明应共同交代：字段含义与类型、必填项、条件必填关系、默认值、允许范围或大小限制、枚举及格式约束。若字段之间存在依赖、互斥或覆盖优先级，应明确表达。列出模型可见的输出结构、可能的结果状态及可恢复的错误；描述会改变状态、访问外部资源、产生费用或需要用户确认的副作用。不要承诺 schema 或实现并不保证的结果。

若协议提供行为注解（例如只读、破坏性、幂等或开放世界提示），注解必须与实际行为一致。注解只是元数据或提示，不是权限检查、隔离、确认机制或执行保证；安全边界必须由运行时授权和实际控制实施。工具描述是模型的操作说明，不是面向人的完整教程；用户文档仍应独立说明配置、权限、操作步骤和故障处理。

以下为结构示意，不是项目中的可调用工具，也不是可复制的真实契约：

```text
名称：example_lookup
描述：按用户提供的资源标识查询只读状态；适用于用户询问该资源当前状态时。不修改资源。
输入：resource_id（必填，字符串）；超出当前契约规定范围时返回参数错误。
输出：当前状态，或有明确类别的未找到/无权访问错误。
副作用：无写入；访问范围仍由运行时授权控制。
```

厂商和协议资料的要求层级不同，使用时应区分适用范围：

- [OpenAI：定义工具](https://developers.openai.com/plugins/plan/tools)：面向 OpenAI 插件的工具规划与描述建议，包括用户目标、选择时机、限制和副作用；仅在相应产品场景中适用，不构成所有模型工具接口的通用协议。
- [Anthropic：定义工具](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)：面向 Anthropic API 的工具名称、描述和 schema 指南；厂商特定建议，不是本项目通用协议规范。
- [MCP 工具规范](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/server/tools.mdx)：MCP 工具发现与调用协议。对声明兼容的 MCP 实现，规范中的协议 MUST/SHOULD/MAY 按其定义和适用版本解释；不得将版本特定要求扩展到非 MCP 工具或其他协议。

## 何时维护文档

评估用户可见影响；当改动改变或揭示以下行为时，更新对应文档：公开行为或工作流、CLI/配置、API/OpenAPI/MCP schema 或描述、安全/策略边界、用户可见界面、发布或迁移行为。选择最贴近读者任务的现有页面；同时检查受影响的示例、链接和必要的双语对应页。若相关页面无需修改，在变更说明或审查记录中简要记录理由；仅内部重排且无用户可见影响时，不要求为形式而改文档。

## 文档审查清单

- [ ] 标题、目标读者、范围和文档角色清晰；内容放在正确的页面，没有复制另一处的权威细节。
- [ ] 当前行为由代码或相应 schema/协议核对；计划、推断和历史信息均有准确状态标记。
- [ ] 内容使用简体中文或符合既有英文页的范围安排；保留的中英文对应页事实一致。
- [ ] 步骤、命令、示例和链接准确、安全且可以按说明使用；占位符明显，不泄露秘密。
- [ ] 涉及工具时，名称、适用目标、输入约束、结果、错误、副作用及注解均忠实反映契约和运行时边界；没有把提示写成强制安全控制。
- [ ] 版本、迁移影响、限制和安全条件已说明；无过期状态陈述或无依据的保证。
- [ ] 相关用户可见变更的文档已更新；未改动的文档如有需要已记录理由。
